# 基础聊天与引用对话

Tibo 先识别现有业务功能：预测、发言、上香、订阅及角色回应等。其他自然语言问题进入基础聊天；也可以明确使用 `ask "问题"`。聊天知道本应用的用途，可以解释概念、讨论 AI 编程、处理文字和回答一般问题，不把所有问题都套成重置规则。回复语言依据当前提问，不依据运行环境。

## 对话规则

- 没有引用：单轮问答，不自动带入此前私聊或群聊历史。
- 引用消息：把同一 Lark 引用链/话题 Thread 作为一个对话，按时间组织人类与本机器人的历史轮次，再加入当前问题。当前问题优先，历史用于理解指代、追问和之前的解释。
- 回复继续引用当前消息，后续引用机器人回复即可继续同一条链。不引用的新消息仍是独立请求，即使刚刚进行过引用对话。
- 普通引用链和平台话题 Thread 都支持；普通链只收集连接到同一根消息的回复，不把附近其他聊天拼进去。不同群、私聊和应用之间不共享历史。
- 群聊仍遵守原有触发与回复预算：引用本身不绕过 @、点名或关键词相关度过滤。私聊可直接追问。

例如先查询最新发言，引用其中的机器人回复问“引导即时生效是什么意思？”，再引用解释问“举一个代码修改的例子”。第二次追问可以看到这条链里原始发言和第一次解释。直接发送同一句问题则不隐式读取前一条帖子。

## 能力与边界

`answer` 开关控制基础聊天、容量摘要和管道文字问答，`router` 用于无引用的自然语言选择业务功能。固定命令优先；引用/话题的其他文字直接作为追问，只调用一次回答；管道 `|ask` 仍处理完整的前序结果，不建立历史。历史只作为对话资料，不能触发历史中的命令、扩大管理员权限或代替二次确认。AI 没有命令行、文件、任意网络请求或账户操作能力。

引用历史由接入层通过固定只读接口按需获取；仅最终准备回复时读取，过滤或限流掉的消息不额外取历史。敏感内容、身份和内部配置会脱敏，历史不作为已核实的重置证据。AI 不可用时给出简短提示，现有固定业务功能继续可用。

## 持久会话与容量

### 核心与平台边界

| 位置 | 职责 |
| --- | --- |
| `src/chat/store.eli` | 按接入方式、应用账户、会话和不透明会话 ID 隔离存储；导入去重、保留角色、追加已确认轮次、版本校验与幂等提交 |
| `src/chat/memory.eli` | 组装既有轮次、计量容量、单次摘要、卸载旧轮次、保留稳定请求前缀和摘要失败降级 |
| `src/chat/session.eli` | 统一处理身份解析的入队顺序和同一对话的串行执行；不同对话各自排队 |
| `adapters/lark/thread.eli` | 解读原始消息、核实平台身份及会话、识别引用链和话题、读取历史、保存平台分页进度，并转换为核心轮次 |
| `adapters/lark/service.eli`、`messages.eli` | 选择普通引用或话题回复、转换 Markdown、调用固定 API、确认平台发送结果及恢复投递账本 |

核心只接收已认证 context、不透明 sessionId、当前消息的不透明标识和标准 user/assistant 文字，不认识平台 ID 格式、引用字段、分页 token 或回复参数。核心的 `through` 是已完成导入的时间水位，接入层负责将它映射成各平台的增量读取范围；模型不接收这些标识或水位。

平台适配器调用核心 `with-session(context, identify, operation)`：identify 由适配器把真实引用解析成会话 ID；operation 在核心的串行范围内导入历史、生成一次回答、发送，并在已确认送达后调用 `commit-turn`。发送成功的判定和发送回执恢复仍由适配器负责，不能把平台发送未知的回复提交为已完成。两个回调只能由程序提供，模型不能定义或调用它们。

其他 IM 只需实现本平台的身份认证、引用读取和回复传输，再调用这些核心接口；无需复制存储、容量摘要或排队逻辑。CLI/MCP 默认单次请求，不因为拥有共用会话能力就自动积累历史。

引用对话按应用、会话及根消息/话题隔离，脱敏后保存在本地。首次从 Lark 导入完整引用链，后续补入新消息，并积累每轮用户输入和已成功发送的 AI 输出。没有引用时不建立或读取这份记录，群关键词插话也不带入旁边的讨论。

历史保持原有 `user` / `assistant` 角色和追加顺序。既有轮次不在每次回答时改写，便于利用提供方的前缀缓存；实际缓存命中由服务端决定。消息附件、撤回内容和其他机器人的消息不作为本机器人的回答。

默认对话输入预算为 900000 token，为当前模型的 1M 上下文预留输出和估算余量。可通过 `TIBO_CHAT_CONTEXT_TOKENS` 调低至 8192，最高 900000。使用服务端返回的输入 token 数作为已知前缀的计量，新增加的文本用 UTF-8 字节数作保守上界，不额外依赖分词库。

接近预算时单独请求一次摘要，融合旧摘要与既有完整轮次，保留目标、事实、纠正、决定和待解问题。成功后卸载旧轮次，从摘要继续追加。摘要失败保留原记录，并提示本次暂不可用；不采用滑动窗口或截断。超过提供方单次容量的历史不会被强行截断后假装完整。

首次导入每次最多读 4 页、读取预算 6 秒，未读完保存进度，下次继续；未导入完整时不生成基于部分历史的回答。后续增量读取同样可续传。普通引用使用普通引用回复，话题使用话题内回复（`reply_in_thread=true`）。同一对话串行处理生成与发送，不同对话可并发；确认发送后才入账，重启恢复不会重复记入。

聊天本身只请求一次回答，没有工具列表、工具调用或循环。只有容量达到阈值时额外请求一次摘要。无引用时的自然语言业务路由、预测分析、独立角色资料采集及管道处理各自遵循原有固定程序，不属于聊天的工具调用。

上下文窗口与缓存机制见[官方上下文规格](https://api-docs.deepseek.com/quick_start/pricing/)和[前缀缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)。
