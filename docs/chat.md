# 基础聊天与引用对话

Tibo 先识别现有业务功能：预测、发言、上香、订阅及角色回应等。其他自然语言问题进入基础聊天；也可以明确使用 `ask "问题"`。聊天知道本应用的用途，可以解释概念、讨论 AI 编程、处理文字和回答一般问题，不把所有问题都套成重置规则。回复语言依据当前提问，不依据运行环境。

## 对话规则

- 没有引用：单轮问答，不自动带入此前私聊或群聊历史。
- 引用消息：把同一 Lark 引用链/话题 Thread 作为一个对话，按时间组织人类与本机器人的历史轮次，再加入当前问题。当前问题优先，历史用于理解指代、追问和之前的解释。
- 回复继续引用当前消息，后续引用机器人回复即可继续同一条链。不引用的新消息仍是独立请求，即使刚刚进行过引用对话。
- 普通引用链和平台话题 Thread 都支持；普通链只收集连接到同一根消息的回复，不把附近其他聊天拼进去。不同群、私聊和应用之间不共享历史。
- 群聊仍遵守原有触发与回复预算：引用本身不绕过 @、点名或关键词相关度过滤。私聊可直接追问。

聊天正文不设单条字符上限，按每次请求的总上下文预算处理；超窗时有限摘要并把完整原文归档，通过内置只读方法按需取回，见 [容量与原文卸载设计](chat-context-design.md)。明确请求不会因为正文长度被静默丢弃。群里未点名的被动关键词插话仍使用独立观察预算，未知管道指令的 AI 修复仍是独立小型任务。

例如先查询最新发言，引用其中的机器人回复问“引导即时生效是什么意思？”，再引用解释问“举一个代码修改的例子”。第二次追问可以看到这条链里原始发言和第一次解释。直接发送同一句问题则不隐式读取前一条帖子。

## 能力与边界

`answer` 开关控制基础聊天、容量摘要和管道文字问答，`router` 根据本轮自然语言选择业务功能，引用中的明确业务请求也适用。固定命令优先；普通引用追问进入聊天，加载真实引用链后，由 read 理解取数需求，再只调用一次回答。路由时准备的单条输入不替代实际对话历史。管道 `|ask` 仍处理完整的前序结果，不建立历史。历史只作为对话资料，不能触发历史中的命令、扩大管理员权限或代替二次确认。AI 没有命令行、任意文件、任意网络请求或账户操作能力；仅能选择程序提供的固定只读方法；网页只允许公开 GET 与固定 DOM 读取，不能自定义网络操作。

引用历史由接入层通过固定只读接口按需获取；仅最终准备回复时读取，过滤或限流掉的消息不额外取历史。历史只隐藏具体凭据、私人路径、内部身份及配置值；提到 API key、余额等普通术语不会删除整条消息。旧版本整段误删的根回复会在再次引用时按核实原文修复，不重置其余轮次、不重新导入已摘要的旧历史。历史不作为已核实的重置证据。AI 不可用时仍返回程序取得的基本资料，现有固定业务功能继续可用。

Lark 原生小表情是独立的 emotion 节点，读取引用时须转换为明确的表情描述，与正文一起提供给 AI；否则模型只能看到文字，会误以为此前没有发送表情。适配器按目录说明内置表情，未知合法类型保留平台 id；角色仍由真实消息发送者决定。当前直接引用每次核实原文，因此不需要清空旧会话或重新导入已摘要历史。该描述仅补齐上下文，不决定新回复该用哪个表情。

基础聊天使用普通对话输出模式，提示词仍可请求带可选表情的结构；模型返回正常文字时也能直接使用。带原生表情目录不再强制开启 API JSON 模式，避免引用中既有普通文字助手轮次时出现空白内容。结构化信号提取等其他任务继续使用自己的输出契约；聊天不会为补一个表情而额外请求模型。

## 内置信息方法

程序先按当前问题准备官方服务状态与事故历史、公开搜索与网页原文、数字计算、时区时间、日期间隔或单位换算，再请求一次 AI 回答。引用“你查查”这类追问时使用该引用链确定主题；不引用时不读旧聊天。能力选择由语义解析完成，结合直接引用、正规历史与此前成功取数的主体，不维护特定问法的关键词规则。普通闲聊不联网，业务预测仍使用自己的核实流程。

引用追问沿着用户的主问题继续。回复中附带的可选建议保持为背景，用户明确选中才成为查询目标。语义解析先声明主题与依据来源，再选择该范围的资料；服务问题不会因附带重置建议而顺便查询发言。首次也校验范围；同时查询服务与重置两类资料，或切换已确认主体，需要当前用户明确请求及原句依据。不是用关键词、正则或本地改写查询来判断。

Lark 在成功发送回复后，把它与源用户消息的标识关联；没有引用时仍是单次请求，不积累聊天正文。引用后，接入层可通过固定消息接口核实直接引用回复及根回复对应的原问题，转换为标准用户文字交给核心。这样即使旧机器人已经答偏，也能理解用户真正追问的主题。核实应用、会话、来源发送人、时间和删除状态；来源不可用则沿用既有引用历史，不猜关联。旧回复没有关联标识时不能凭相邻消息推断，已有投递回执和平台原文可用于本地核实补齐。

搜索最多四条结果，默认继续读取两篇正文；read-page 可读取当前问题或显式引用资料中已有的公网链接。按来源标明正文、部分内容或访问受限，不能把只有标题的结果当具体规则依据。官方状态、搜索分别缓存并合并并发；离线模式不联网。计算是有限浮点算术解析，不执行代码。AI 失败仍保留资料或计算结果，资料失败如实说明未知。开关、缓存与后备入口见 [内置信息能力](chat-builtins.md)。

## 持久会话与容量

### 核心与平台边界

| 位置 | 职责 |
| --- | --- |
| `src/chat/store.eli` | 按接入方式、应用账户、会话和不透明会话 ID 隔离存储；导入去重、保留角色、追加已确认轮次、版本校验与幂等提交 |
| `src/chat/memory.eli` | 组装既有轮次、计量容量、单次摘要、卸载旧轮次、保留稳定请求前缀和摘要失败降级 |
| `src/chat/session.eli` | 统一处理身份解析的入队顺序和同一对话的串行执行；不同对话各自排队 |
| `adapters/lark/thread.eli` | 解读原始消息、核实平台身份及会话、识别引用链和话题、读取历史、保存平台分页进度，并转换为核心轮次 |
| `adapters/lark/service.eli`、`messages.eli` | 选择普通引用或话题回复、转换 Markdown、调用固定 API、确认平台发送结果及恢复投递账本 |

核心只接收已认证 context、不透明 sessionId、当前消息的不透明标识和标准 user/assistant 文字，不认识平台 ID 格式、引用字段、分页 token 或回复参数。核心的 `through` 是已完成导入的时间水位，接入层负责将它映射成各平台的增量读取范围；模型不接收这些标识或水位。

平台适配器调用核心 `with-session(context, identify, operation)`：identify 由适配器把真实引用解析成会话 ID；operation 在核心的串行范围内导入历史、生成一次回答、发送，并在已确认送达后调用 `commit-turn`。发送成功的判定和发送回执恢复仍由适配器负责，不能把平台发送未知的回复提交为已完成。两个回调只能由程序提供，模型不能定义或调用它们。

其他 IM 只需实现本平台的身份认证、引用读取和回复传输，再调用这些核心接口；无需复制存储、容量摘要或排队逻辑。CLI/MCP 默认单次请求，不因为拥有共用会话能力就自动积累历史。

引用对话按应用、会话及根消息/话题隔离，脱敏后保存在本地。直接引用的角色和正文独立提供，平台标识不进入模型；此前成功取数的主体随确认轮次保存，摘要卸载后仍保留。主体切换需要语义计划引用当前用户明确换题的原句，旧机器人建议不能自行换题。首次从 Lark 导入完整引用链，后续补入新消息，并积累每轮用户输入和已成功发送的 AI 输出。没有引用时不建立或读取这份记录，群关键词插话也不带入旁边的讨论。

原问题来源关联由平台适配器负责；核心只接收 `initialRequest`、`quotedRequest` 的标准 user 文字，以及语义解析的 `scope`，不认识平台消息标识。新主题只有实际成功取得对应资料后，才作为已确认取数主体保存；失败计划、失败资料和旧混合结果的数组顺序不能建立新主体。查询范围与结果一同提供给回答阶段，主题理解和范围校验仍只使用原有一次 read 请求，不增加模型往返。

历史保持原有 `user` / `assistant` 角色和追加顺序。既有轮次不在每次回答时改写，便于利用提供方的前缀缓存；实际缓存命中由服务端决定。消息附件、撤回内容和其他机器人的消息不作为本机器人的回答。

默认对话输入预算为 980000 token，为当前模型的 1M 上下文预留输出和估算余量。`TIBO_CHAT_CONTEXT_TOKENS` 可调低摘要触发目标，最高 980000。已有稳定前缀使用服务端返回的 token 计量，新文本以 UTF-8 字节数作保守上界。

超过预算时先保存原文，再有限摘要旧历史或超大当前材料；一次请求最多 3 次摘要。摘要失败或次数用完时保留文件索引与已完成部分，未读取的内容保持未知。原文归档随会话持久保存，`context-read` 在既有一次只读资料准备中按需取回，不新增工具循环。单轮未引用请求也不会因此开始累计历史。

首次导入每次最多读 4 页、读取预算 6 秒，未读完保存进度，下次继续；未导入完整时不生成基于部分历史的回答。后续增量读取同样可续传。普通引用使用普通引用回复，话题使用话题内回复（`reply_in_thread=true`）。同一对话串行处理生成与发送，不同对话可并发；确认发送后才入账，重启恢复不会重复记入。

回复位置与聊天历史是两个机制。香客信息、help、固定查询、错误提示及额外庆典消息同样保持来源话题或引用位置，但这些业务回复不会因此读取或积累 AI 对话历史。在话题内点击 🙏 时，以被点击消息为回复目标；已知机器人消息复用本地话题元数据，旧回执首次核实后补齐。庆典的回复目标随发送回执保存，拒收重试和重启续发仍在原话题。

聊天最多先请求一次独立 read 语义解析，程序按整批校验的固定方法并发准备资料，再请求一次回答；没有工具列表、工具调用或循环，也不会根据回答再查询。只有容量达到阈值时额外进行有限摘要，整轮最多 3 次。无引用时的自然语言业务路由、预测分析、独立角色资料采集及管道处理各自遵循原有固定程序，不属于聊天的工具调用。

上下文窗口与缓存机制见[官方上下文规格](https://api-docs.deepseek.com/quick_start/pricing/)和[前缀缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)。
