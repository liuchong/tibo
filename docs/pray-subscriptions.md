# 上香与订阅

这些功能需要可信的本人身份。它们是应用业务功能，Lark 只负责接收消息、提供真实身份和投递；未来其他 IM 可以复用同一核心。

## CLI 上香与档案

```bash
tibo pray
tibo query '🙏'
tibo query 'pray me'
tibo query 'pray board 10'
tibo query 'pray stats'
```

CLI 自动使用进程真实 UID，作用域为本地会话，不需要传档案参数，也不能通过命令参数假冒另一个人。档案保存在当前 `TIBO_STATE_DIR` 中；同一 UID、同一状态目录会持续累计。同一接入应用内的同一真实账号，在私聊和所有授权群共用个人档案；不同群的愿力池与榜单分别记账。CLI 不会自动合并 Lark 档案，不同 IM 也不会仅凭同名合并。

`pray me` 是本人档案，`board` 是当前会话匿名榜单，`stats` 是当前会话愿力池。榜单只展示“香客001”一类编号，不公开系统 UID、open_id 或真实姓名。MCP 没有可信个人身份，不记录上香。

个人编号按首次上香顺序分配，跨接入方式共用编号序列，管理员没有预留编号。因此先用 CLI 上香会领取 001，随后在 Lark 上香会领取另一个编号；它们未经过账号绑定，不能自动当成同一个人。个人编号与各会话榜单的匿名编号可能不同。

## 旧档案迁移

首次读取或上香会在锁内自动迁移旧会话档案。相同真实身份的累计次数、功德合计，取最早首次时间、最晚最近时间，合并成就；当前日期的次数合计。旧文件没有完整逐日历史，因此连续天数保留最近日期的已记录连续值，最长值取已有最大值，不推测跨会话缺失的打卡。

新数据统一保存在 `pray-identities.json`，一次原子写入完成迁移；旧 `pray-<摘要>.json` 原样保留作恢复依据，不重复导入。会话榜单保留各群匿名编号，个人编号统一重新排序；群榜单不泄露其他群活动。新上香与对应群记账在同一文件提交，避免只写入其中一份。不要手动删除新文件来重新迁移。

## 上香会发生什么

每次新请求计一次 🙏。同一人在任意会话距上次计功德不足 15 秒时仍增加上香次数，但不再增加功德；重复投递同一请求返回原回执，不重复计数。

- 功德称号和回复随累计进度变化，从“初来香客”逐步进阶。
- 个人功德在 1、3、10、30、50、100、233、500、1000 触发成就与彩蛋。
- 会话累计上香次数在 10、50、100、233、500、1000 解锁集体彩蛋；快速连发的有效新事件也算，个人功德冷却不影响这个进度。
- 按北京时间记录每日次数、连续打卡和最长连续天数；连续 3 天、7 天有额外成就。

档案、功德和成就使用本地规则。每次新上香附加一句含 token 的吉祥话；启用 wish 时可由模型生成（最多等 1.5 秒），否则随机本地祝词兜底。先保存祈祷再生成，重复请求不重复计数或调用模型；查询档案、榜单、统计不调用 wish。详情见 [祈祷祝词](oracle.md#已接入祈祷吉祥话)。语义识别“帮我上香”等请求可能使用 router。所有功德和愿力均与预测数据隔离，不影响真实概率，也不兑换额度。

## 集体彩蛋与快速连发

第十次解锁“十炷成阵”：回复会出现独立的 **🎉 集体彩蛋** 标题、十炷电子香和群体 token 祝愿；后续里程碑有不同的仪式。`pray stats` 或“什么集体彩蛋？”可以查看当前会话已解锁的仪式。

群回复限频只限制开口，不丢上香。限频时已解锁但未展示的彩蛋保存在档案，下一次允许回复的上香会展示；不会补发每一条旧祈祷。多人同时达到里程碑时只预留一次展示，平台确认发送成功后才标记已展示；明确拒绝则释放展示名额，未知发送结果保留占用供运维核对，避免重复刷屏。CLI 返回回执时即视为展示。

旧档案计数和已解锁成就保留。升级后尚无展示标记的旧集体彩蛋，会在下一次允许回复的上香回执中展示一次；按累计次数补齐里程碑，不增加个人功德。已有彩蛋的会话统计始终可查看，不依赖 AI 理解彩蛋是什么。

所有档案读改写经过短事务队列和跨进程文件锁，锁内只记账，不等待 AI 或平台发送。接入层使用磁盘事件队列，祈祷先提交记账再执行可选祝词；暂时未记账成功的事件保留重试。并发回复可能重排，档案查询才是当前累计值，不能只数机器人回了几条。具体缓存和工作线程策略见 [Lark 投递](lark.md#投递与重复消息)。

## Lark 的 🙏

Lark 的“双手合十”反应类型为 `THANKS`。接入层分别处理两种情况：

1. 在授权群里发送含 Unicode 🙏 或 Lark 原生 `[双手合十]` 的文字消息，只要平台把该消息交给机器人，即使没有 @ 也可以上香；点名查询需 @ 当前机器人或在文字中包含 tibo（不区分大小写）；次级关键词需经过 [相关度与降敏](im-triggers.md) 后才回应。
2. 对授权群或私聊中平台可读取的消息点击“双手合十”反应，记一次上香。平台重投同一创建事件不重复计数；取消后再次添加若产生新的创建事件，则再计一次次数，功德仍按冷却规则计算。一次消息中多个🙏算一次请求；移除表情本身不算上香。

平台权限或群设置可能不交付未 @ 的消息，程序不会凭空读取它。反应可指向本机器人或群成员消息，正文只作为祝词参考；无法读取和核实会话的消息、未授权群的反应不会记账。详见 [Lark 接入](lark.md)。

## 订阅私聊报告

在已接入的 IM 中发送固定指令，或启用 router 后用语义请求：

```text
subscribe
subscription
unsubscribe
帮我订阅早晚报告
取消我的订阅
```

订阅只能操作本人，不能指定其他收件人。CLI 和 MCP 没有可用的 IM 私聊身份，因此不能创建订阅。Lark 的身份由实际事件获得，订阅按应用账户隔离，在同一应用的不同群里仍是同一份本人订阅。

时间固定为每天北京时间 **09:00 和 21:00**，没有其他时点，也没有用户自定义时间、周期或时区。订阅从下一定点生效，不额外立即生成一次报告；退订不影响群推送和其他订阅者。

## 定点生成与投递

定点调度由运行中的 IM 接入层触发，核心提供共享报告生成。只运行采集 daemon 不会发送 IM 报告。

每个 UTC 定点键对应一份报告：先锁定并生成，再把相同正文发送到授权群和有效订阅者。人数增减只改变投递数量，不改变预测、AI 调用或报告生成次数。订阅私聊推送的正文完全相同。

进程必须在 09:00 或 21:00 那一分钟运行；错过不补发。生成失败或中断的定点保留状态，不自动重跑。发送队列可能在定点后继续投递，最多持续 15 分钟，这是同一次发送任务，不是新增推送时间。单个收件人失败不会使其他人的报告重新生成或停止发送。

投递前重新检查订阅是否仍有效。Lark 私聊需要用户在应用可用范围内且平台允许机器人给他发消息；订阅成功本身不是私聊送达证明。投递状态与实际验收见 [Lark 接入](lark.md#投递与重复消息)。
